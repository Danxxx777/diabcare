Constitución del proyecto DiabCare Hospital
Propósito y contexto
DiabCare Hospital es una plataforma SaaS de analítica clínica hospitalaria orientada a la gestión integral de pacientes con diabetes y comorbilidades. El sistema integra un HIS modular (admisiones, agenda, consulta externa), un data Waterhouse de 63 tablas en modelo Hecho-Dimensión, pipelines ELT y modelos de machine learning para apoyo a la decisión clínica.
Problema de negocio
Fragmentación de datos clínicos entre sistemas operativos y analíticos.
Dificultad para obtener KPIs de prevalencia, control metabólico y riesgo.
Falta de trazabilidad entre objetivos estratégicos (definidos en el avance anterior) e implementación.
Necesidad de cumplir gobernanza SDD antes de codificar funcionalidades.

Principios fundamentales
Principio I. SDD: No se programa lo que no está especificado. Open API antes de implementar.
Principio II. Paquetes: 15 paquetes funcionales P1–P15 en backend/paquetes/, backend/nucleo/ y frontend/paginas/{departamento}/.
Principio III. Integridad DWH: Modelo Hecho-Dimensión; ELT PocketBase→Airflow→MinIO→API.
Principio IV. Pruebas primero: pytest bajo pruebas/; endpoints nuevos con pruebas API.
Principio V. Seguridad: JWT HS256, roles, auditoria en operaciones sensibles.
Principio VI. Trazabilidad: OE→OT→OO→Departamento→Paquete→CU→Historia de usuario.

Arquitectura y stack
Backend Python 3 + FastAPI. Frontend Vanilla JS. Almacenamiento MinIO/Parquet. Orquestación Airflow. ML scikit-learn. Autenticación JWT (usuarios en MinIO). Fuente origen PocketBase (~100K registros). Despliegue demo: uvicorn Principal.py puerto 8000.

CU-O01: Iniciar sesión con JWT
Atributo
Valor
Paquete
P1 Autenticación
Actor principal
Administrador, medico, analista
OE / OT / OO
OE4 / OT4.1 / OO5.1.1
Ruta en aplicación
http://localhost:8000/ → Iniciar sesión → Dashboard
Precondiciones
El servidor Uvicorn está activo en el puerto 8000.
Existe al menos un usuario registrado con rol valido.
El navegador tiene JavaScript habilitado.
No hay sesión JWT activa en localStorage.
Flujo principal
1. El actor abre la pantalla de login.
2. Ingresa correo electrónico y contraseña.
3. El frontend envía POST /api/auth/login.
4. El backend valida credenciales contra usuarios.parquet en MinIO.
5. Se emite token JWT HS256 con rol y expiración.
6. El frontend almacena el token y redirige al dashboard.
7. La barra lateral muestra solo módulos permitidos para el rol.
8. Se registra evento de acceso en auditoria (P11).
Flujos alternos y excepciones
Credenciales invalidas → HTTP 401, mensaje genérico sin revelar campo.
Token expirado → redirección a login al invocar API protegida.

HU-O01: Iniciar sesión con JWT
Atributo
Valor
Identificador
HU-O01
Título
Iniciar sesión con JWT
Stakeholder / Actor
Usuario del sistema (administrador, médico o analista)
Descripción de la necesidad
El sistema debe permitir la autenticación segura mediante correo electrónico y contraseña, validando credenciales contra usuarios.parquet en MinIO y emitiendo un token JWT (HS256) que identifique el rol del usuario.
Historia de usuario (Como / Quiero / Para)
Como usuario del sistema, quiero iniciar sesión con correo y contraseña, para acceder únicamente a los módulos autorizados según mi rol.
Justificación (Rationale)
Base de seguridad del SaaS; sin sesión válida no hay acceso a datos clínicos ni analítica.
Prioridad
Alta
Supuestos y restricciones
JWT HS256; usuarios en MinIO (no PocketBase); contraseñas hasheadas; RG-005 auditoría.
Trazabilidad OE / OT / OO
OE4 / OT4.1 / OO5.1.1
Caso de uso vinculado (CU-O)
CU-O01
Paquete funcional
P1 Autenticación
Departamento
Seguridad e Identidad
Requisitos funcionales (RF)
RF-O-P01-001, RF-O-P01-002, RF-O-P01-006
Reglas de negocio (RN / RG)
RN-O-P01-001, RN-O-P01-002
Criterio de aceptación
CA-01: Dado un usuario registrado con credenciales válidas, cuando envía POST /api/auth/login, entonces recibe HTTP 200 con token JWT y rol.
Criterio de aceptación
CA-02: Dado credenciales inválidas, cuando intenta iniciar sesión, entonces recibe HTTP 401 con mensaje genérico.
Criterio de aceptación
CA-03: Dado un token válido, cuando carga la aplicación, entonces el menú lateral muestra solo módulos de PERMISOS_MODULOS.
Criterio de aceptación
CA-04: Dado login exitoso, cuando accede a módulo no permitido, entonces recibe HTTP 403.
Criterio de aceptación
CA-ERR: Errores HTTP según tabla de códigos (§ Historias de usuario).
Método de verificación
Prueba funcional, inspección de respuesta API y demo en /paginas/seguridad/autenticacion/index.html

Descripción de la necesidad
El sistema debe exponer documentación OpenAPI autogenerada de la API REST para integradores y partners (OO2.1.2 del avance estratégico anterior).
Historia de usuario (Como / Quiero / Para)
Como administrador o integrador, quiero consultar la documentación OpenAPI interactiva, para conocer contratos, esquemas y probar endpoints.
Justificación (Rationale)
Escalabilidad comercial vía APIs (OE2) — base para CU-O13 partners.
Prioridad
Baja
Supuestos y restricciones
Swagger UI en /docs; endpoints partners aún no implementados.

pytest debe ejecutarse sin errores en entorno de desarrollo.

Mocks de MinIO/JWT para pruebas sin infraestructura externa.
Diseño de la base de datos
DiabCare no utiliza un RDBMS tradicional como almacén analítico principal. La base de datos del sistema es MinIO (object storage) con archivos Parquet columnar, organizados en buckets y prefijos según el modelo Hecho-Dimensión (star schema). PocketBase aloja únicamente ~100K registros de origen para el ELT; usuarios, JWT y credenciales residen en MinIO (usuarios.parquet).

Anexo A
El documento estratégico del avance anterior del proyecto establece la cadena BSC → OE → OT → OO y 59 casos de uso en tres niveles (CU-E, CU-T, CU-O). avance operativo actual consolida el nivel operativo implementado en el avance actual del sistema en ejecución, especificación SDD y UML.
A.1 Flujo de valor del avance estratégico anterior
Operativo: PocketBase aloja ~100K registros origen; MinIO es la BD (usuarios/JWT, Parquet clínico).
Táctico: Airflow orquesta ELT hacia MinIO.
Estratégico: Dashboard, reportes y benchmarking alimentan decisiones.
